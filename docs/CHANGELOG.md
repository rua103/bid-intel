## 2026-09-24 · 模型抽取排障：从 0 条到 19 条

起点：模型抽取**每次请求都拿不到结果**。`clean-compare-3.json` 里 6 次请求全部 `ReadTimeout`，耗时齐刷刷停在 45.7～45.9 秒，成功响应数为 0。

排查过程（每一步都留下了可复用的结论）：

1. **先排除地址与 Key。** 本机模型名 `deepseek-v4-flash`（早期实验用的是 `deepseek-v4-pro`）；连通性测试通过，一次简短 JSON ping 返回 HTTP 200、约 3.4 秒。不是鉴权或地址问题。
2. **把超时从 45 秒提到 120 秒——无效。** 两条测试公告仍各自 `ReadTimeout`（一条 30 条规则表格候选，另一条 3 条）。真因是 `httpx` 的 `timeout` 是**读超时**，非流式下服务端生成完成前一个字节都不发，于是它退化成"整段生成总时长上限"。**任何超时值都救不了非流式请求。**
3. **改为 `httpx.stream` 读 SSE。** 6 次请求全部成功返回——但**抽出来的东西是坏的**：3 条公告里 1 条返回空内容、2 条 `JSONDecodeError`，都是输出被 `max_tokens` 截断的结果。
4. **试过 `thinking: {"type": "disabled"}` 和 `reasoning_effort: none`，两个都适得其反**：推理 token 反而上升（119 → 548），`content` 返回空串，延迟翻三倍。
5. **定位真因。** `deepseek-v4-flash` 是重推理模型，真实公告下会先烧掉约 5000 个推理 token 才输出正文，直接撞穿 `max_tokens=4096`。有效的关闭方式只有 `chat_template_kwargs: {"enable_thinking": false}`；三个顶层同名字段**全部被网关忽略**。

> ⚠️ **一个陷阱**：第 4 步里"不带任何参数看起来正常"（11.02s / 119 推理 token）是在**十几个 token 的短 ping** 上测的。换成真实公告（12000 字符）结论完全相反。**别用短 prompt 下结论。**

结果（同一份语料、同一个模型、同样 6 次请求）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `model` 模式标的数 | 0 | **19** |
| `model` 模式主体数 | 0 | **2** |
| `hybrid` 模式标的数 | 32 | **51** |
| 输出 token | 24576 | 5494 |
| 总耗时 | 1216.3s | **291.6s** |
| 单条耗时 | 210 / 216 / 200s | 24.5 / 35.9 / 88.7s |
| 抽取成功的公告数 | **0 / 3** | **3 / 3** |

两份原始结果都在 [`benchmarks/`](benchmarks/)：`stream-compare-3-reasoning-on.json`（即上表"修复前"）与 `stream-compare-3.json`。

**计费**：排障期间用 `model_call_budget` 限制了请求次数，但超时请求是否计费取决于服务商，需由团队查看服务商 usage/billing。修复后的 6 次请求都有本地 token usage 可核验。

对应提交：`a95be2f`（流式改造）、`5763752`（关闭推理）。
