# 官方数据接入与批量处理

本文说明附件依赖、中文 ZIP、数据集隔离和后台续跑。2026-09-26 已在独立数据集完成 1038 条官方公告的 `rules + RapidOCR` 批处理，实际结果、完整性核验及告警见 [官方接入检查](OFFICIAL_INTAKE_REVIEW.md)。全量写入完成不等于字段准确或附件全部可用；本轮没有 gold，也没有调用模型。

## 部署附件解析依赖

在 backend 虚拟环境中运行：

```powershell
python -m pip install -e ".[dev]"
```

基础依赖现在包含 xlrd（旧 XLS）、pdfplumber（PDF 表格）、pypdfium2（PDF 渲染）、Pillow、olefile（识别旧 Office 流）、filelock（跨进程锁）、py7zr 和 rarfile。OCR extra 安装 RapidOCR 与 ONNX Runtime：

```powershell
python -m pip install -e ".[dev,ocr]"
```

RapidOCR 的模型首次启动时下载到本机模型缓存；OCR 识别文本会在数据库目录的 ocr-cache 中复用。官方扫描件仍须核验识别质量，不能把 OCR 输出当作人工 gold。

旧 DOC 使用 LibreOffice 无界面转换为 DOCX，然后读取段落和表格。安装 LibreOffice 后，在 backend/.env 中按实际位置填写，例如：

```dotenv
LIBREOFFICE_PATH=C:/Program Files/LibreOffice/program/soffice.exe
DOCUMENT_CONVERSION_TIMEOUT_SECONDS=120
```

未显式配置时会检查 PATH、Windows/macOS 常见安装目录，以及 backend/.data/tools/libreoffice/program/soffice.exe。本次开发机使用 LibreOffice 26.2.6.3，从官方 MSI 管理解包到项目本地目录，未设为系统默认 Office；工具文件不入 Git。新机器仍需安装 LibreOffice，不能只复制源码便宣称 DOC 可用。

每次转换使用独立输入/输出临时目录，跨进程锁串行复用应用专属 LibreOffice 配置，将宏安全级别设为最高。默认和最高转换时限均为 120 秒；锁队列最多等待 300 秒，分别给出转换/排队超时提示。旧 .env 若显式写了 60 秒仍会覆盖默认值，需要改成 120 后重启后端。超时会终止该次转换进程树。

成功且通过 ZIP 校验的结果按内容 SHA-256、转换器路径和修改时间缓存到原数据库目录的 document-cache；同内容不同文件名复用结果，坏缓存重建，失败不缓存。缓存仅本地、不入 Git，目前没有自动容量淘汰。原始文件不会改名或写回；按内容识别旧 DOC、DOCX、XLS、XLSX、HTML、PDF 和图片，无扩展名也能进入对应分支。后台任务支持受控落盘展开 ZIP、RAR、7z；RAR 依赖可用的 7-Zip、bsdtar 或系统解码工具。扩展名可识别不等于所有压缩成员都能解码，损坏成员会保留警告。

本次发现 LibreOffice 26.2.6.3 对其自身导出的某个旧 DOC 有表格回读兼容问题；Word 16 保存的同表格可正确转换。对“读到 DOC 文本但没有标的表格”的情况会显式警告，不能把转换成功退出等同于七字段提取成功。

后端启动后访问 GET /api/v1/parser-capabilities；前端导入区也显示缺失依赖。

| 能力字段 | 表示什么 |
|---|---|
| legacy_doc | 能找到 LibreOffice 程序；仍需用 DOC 冒烟样例验证程序可运行 |
| legacy_xls | xlrd 可导入 |
| pdf_text / pdf_tables / pdf_render | PDF 文本、表格、渲染组件可用 |
| image_ocr | 检查所选 OCR 引擎依赖（默认 RapidOCR）；不代表 OCR 已启用或识别质量合格 |

默认 RapidOCR 本地模型同时覆盖中文与英文，不依赖 Tesseract。OCR_ENABLED=true 时，图片和 PDF 无文本扫描页会识别并保存文本；PDF 页数默认上限 1000，每份最多 OCR 1000 个扫描页，可用 PDF_MAX_PAGES / PDF_MAX_OCR_PAGES 配置。全量官方运行实际产生 2261 条 RapidOCR 识别结果提示，覆盖 359 条公告；21 条提示未识别到可信文本。图片文本会尝试按制表符识别字段表头；无边框、跨页或嵌套复杂表格仍需人工核验。

## 选择干净的数据集

在页面「当前数据集」填写名称，例如「官方数据第一轮」，点击「新建空数据集并切换」，确认页头显示 0 条公告再导入。重跑时再建一份空集，原数据可随时切回查看。

- default 始终对应原来的 DATABASE_PATH。历史开发数据保留。
- 新数据集使用原库所在目录下 `datasets/<随机 ID>.sqlite`。每库包含完整业务表和自己的名称。
- 导入、数量统计、标的物检索、主体列表、五类关系查询、SQLite 关系图均使用当前数据集。
- 导入过程中界面禁用切换。切换会清掉旧查询结果、主体选项、文件选择；旧请求晚到的结果不会写入新页面。
- 模型配置是全局配置，保持原位置；标注工作台仍使用独立 gold/predictions JSON，不随业务库清空或切换。

脚本客户端：POST /api/v1/datasets，JSON 为 {"name":"官方数据第一轮"}；响应返回 id。所有业务请求带 `X-Dataset-ID: <id>`。不带 header 时使用 default；未知 ID 返回 404、无效 ID 返回 422，绝不静默回到默认库。GET /api/v1/datasets 可列出数据集与公告数。服务端不保存全局的“当前数据集”，因此不同浏览器可并行选择不同库。

本轮没有删除/清空接口。新建空集提供干净重跑入口；磁盘清理由后续明确的数据保留策略处理。Neo4j CLI 是独立流程，使用时仍须显式指定 SQLite 路径与对应 Neo4j dataset，网页切换不会自动重新同步 Neo4j。

## 大压缩包与后台续跑

官方材料应放在后端运行主机可读的同一目录：每条公告用同名 .html 和可选同名 .zip/.rar/.7z。页面「大批量后台处理」输入后端本机目录、模式和 OCR 选项；默认 rules + 本地 OCR 不调用付费模型。浏览器不上传几 GB 文件，后端按一条公告展开并处理，然后写入当前数据集。可关闭浏览器，任务进度仍保存于数据库目录下 jobs/<任务ID>。

每条公告单独校验源文件 SHA-256，处理阶段状态、当前附件和成功解析缓存落盘；成功入库使用任务ID/公告序号幂等键，提交数据库后即使进程在写进度前退出，也不会重复导入。API 可查询任务列表/报告、请求暂停、继续和重试失败公告。若服务重启，任务状态显示 interrupted，点续跑后跳过已完成公告并复用文件解析缓存。新建任务时如果材料发生变化，必须重新建任务。

压缩内容流式写入临时目录，不依赖 200 MiB 内存展开限制。默认每公告展开总量 2 GiB、单成员 512 MiB、深度 8 层、成员 20000，3 个工作进程；均可通过 JOB_MAX_* 与 JOB_WORKERS 设置。ZIP/7z 以应用生成的安全临时名落盘，归档内路径只用于 source_file 溯源，不能越出临时目录。RAR 使用随项目本机管理的 7-Zip 可执行程序或系统解码工具；不要把工具二进制提交 Git。本次官方全量任务解析了 14174 个叶文件（含 HTML），其中 239 个来自 RAR、13 个来自 7z；仍有 1 个压缩成员无法读取，不能把任务 completed 理解为所有附件均完整。

从命令行启动（后端虚拟环境内）：

```powershell
python -m app.jobs create D:/path/to/official-data --name "官方全量规则与OCR" --mode rules --start
python -m app.jobs status <任务ID>
```

纯模型/混合模式会对材料调用已配置模型并产生费用；要跑规则基线请明确用 rules。任务成功只说明管线处理完成，不代表识别正确。每条材料的警告和失败原因须在处理报告中核查。

## ZIP 文件名和异常核对

支持 UTF-8 标志、带 CRC 校验的 Info-ZIP Unicode Path 扩展，以及未置标志的 UTF-8/GB18030（兼容常见 GBK）。按 ZIP 成员对象读取原始数据，文件名只作溯源和分组，不解压到磁盘。

自动修正编码会出现在 warnings；无法判断编码时保留原名并要求核验；解码后重名会跳过后续同名成员并警告。损坏/加密/压缩算法不支持的成员会列入警告。整包没有可处理文件时，接口返回具体原因；存在有效公告时继续导入，顶层 warnings 保留坏包提示。未唯一匹配的附件仍保留在 orphan_files，并明确提示未导入。

验证码、维护页、访问限制和 JSON 下载错误会被标为“源附件不可用”并排除出解析/模型流程，原路径仍在 warnings。支持先解开 gzip 封装再检查；这类文件的字段缺失属于源材料问题，不应计为模型抽取失败。不会自动重新下载或替换材料。

有 HTML 正文时，按附件叶文件名识别明确招标/磋商/采购文件；保留 source_files，排除其成交标的、主体和元数据抽取。已识别的空模板同样保留来源并警告。HTML 明确需求表不进入模型上下文。该分类仍需人工核验；单独解析采购附件仍可读取内容。跨文件重复只在包号、型号、金额等兼容且可唯一匹配时合并，双方证据写入 source_evidence；冲突和歧义保留并提示，不能直接把候选数量当最终成交数量。

不能可靠推断所有编码，也不能只靠文件名恢复所有对应关系。中文能读不等于归属必然正确，尤其多公告共用“报价表.pdf”时，应按公告编号分目录或分批上传。交互式上传 ZIP 的守卫仍为最多 3 层、2000 个成员、累计展开数据 200 MB；上述后台任务使用独立可配置的落盘预算。

## 后续批次与人工核验

1. 安装上述依赖并确认能力检查；以本机 DOC/XLS/PDF 样例跑通后再接官方附件。
2. 新建空数据集，先导入一小批含各附件类型的材料，核对公告数、未匹配附件、逐公告 warnings 和七字段来源。
3. 若出现缺依赖、未匹配或文件损坏，先处理并在新数据集中重跑；不要把缺附件的结果直接用于 gold 标注。
4. 测量实际材料在 rules/hybrid/model 下的单篇耗时、模型失败与输出量，再决定分批规模。完成全量后核对总公告数和失败清单。
5. 再开始独立人工标注、三方案评测和任务二答案核对。

本次 1038 条规则 + OCR 任务已通过逐公告检查点完成，首轮 13 条状态写入失败和 8 条外层 ZIP 识别错误经修复后续跑，最终 1038 条完成、0 条失败。活动处理墙钟时间按检查点估算约 66 分 45 秒，使用 3 个工作进程；此值是本机规则/OCR 管线基线，不是模型吞吐或赛事计分结果。当前导入了 6814 条未核验标的候选，但没有投标参与或中标记录；87 个无效下载附件、少量不支持格式和损坏成员仍需人工/数据方核对。模型模式与混合模式的耗时、输出及评分仍需单独实验，参见 [官方接入检查](OFFICIAL_INTAKE_REVIEW.md) 和 GAP 1.13。
