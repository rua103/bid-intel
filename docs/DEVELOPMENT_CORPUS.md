# 开发集与实验记录

`backend/app/corpus.py` 是受限速率的公开开发集采集器。它只允许 `ccgp.gov.cn`，默认每次请求至少间隔 1 秒，记录来源 URL、响应状态、下载时间、文件大小和 SHA-256；第三方附件域名会被明确记录为跳过。采集器不访问官方隐藏评测集，也不把公开开发集当作官方成绩。

2026-09-24 已按中标/成交公告路径重新采集一份开发集：站点当前列表提供 20 条公告，清单位于本机 `backend/.data/development-clean/`，原始文件不纳入 Git。旧目录保留作为审计记录，但包含误发现的站内资讯，不用于实验。

`docs/benchmarks/clean-compare-3.json` 是其中 3 条公告的规则、纯模型和混合方案对比。规则抽取正常完成；当时 DeepSeek 的 6 次请求全部 `ReadTimeout`，成功响应数为 0，所以这份文件不能被解释为模型准确率。它记录的是**修复前**的状态，只作历史留存——修复后的对比见 `stream-compare-3.json`（排障经过见下文）。

`docs/benchmarks/synthetic-1000.md` 是离线合成压测：1000 条公告、2000 条标的、3000 条显式注入投标记录。它用于建立 SQLite 查询基线，不用于证明抽取准确率。五个场景的 warm p95 都低于 1 秒，最慢的共同投标项目查询约 325 ms。

## DeepSeek 抽取排障记录（2026-09-24，已解决）

这一节保留完整的失败路径，因为每一步都留下了可复用的结论。

**起点**：模型抽取每次请求都拿不到结果。`clean-compare-3.json` 里 6 次请求全部 `ReadTimeout`，耗时齐刷刷停在 45.7～45.9 秒，成功响应数为 0。

**排查过程**：

1. **先排除地址与 Key。** 本机配置的模型名是 `deepseek-v4-flash`（早期实验用的是 `deepseek-v4-pro`）；连通性测试通过，一次简短 JSON ping 返回 HTTP 200、约 3.4 秒。不是鉴权或地址问题。
2. **把超时从 45 秒提到 120 秒——无效。** 两条测试公告仍各自 `ReadTimeout`（一条 30 条规则表格候选，另一条 3 条）。真因是 `httpx` 的 `timeout` 是**读超时**（等下一块字节），非流式下服务端生成完成前一个字节都不发，于是它退化成"整段生成总时长上限"。**任何超时值都救不了非流式请求。**
3. **改为 `httpx.stream` 读 SSE。** 这一步之后 6 次请求全部成功返回——但**抽出来的东西是坏的**：3 条公告里 **1 条返回空内容、2 条 `JSONDecodeError`**，都是输出被 `max_tokens` 截断的结果。
4. **试过 `thinking: {"type": "disabled"}` 和 `reasoning_effort: none`，两个都适得其反**：推理 token 反而上升（119 → 548），`content` 返回空串，延迟翻三倍。
5. **定位真因。** `deepseek-v4-flash` 是重推理模型，真实公告下会先烧掉约 5000 个推理 token 才输出正文，直接撞穿 `max_tokens=4096`。有效的关闭方式只有 `chat_template_kwargs: {"enable_thinking": false}`；三个顶层同名字段（`thinking` / `enable_thinking` / `reasoning_effort`）**全部被网关忽略**。

**结果**（同一份语料、同一个模型、同样 6 次请求）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `model` 模式标的数 | 0 | **19** |
| `model` 模式主体数 | 0 | **2** |
| `hybrid` 模式标的数 | 32 | **51** |
| 输出 token | 24576 | 5494 |
| 总耗时 | 1216.3s | **291.6s** |
| 单条耗时 | 210 / 216 / 200s | 24.5 / 35.9 / 88.7s |

两份原始结果都在 `docs/benchmarks/`：`stream-compare-3-reasoning-on.json`（推理未关，即上表"修复前"）与 `stream-compare-3.json`（已关）。

**仍未解决**：抽出来的字段很不完整——那条 15 标的的公告只填了 `product_name` 和 `quantity`，其余五个字段全空。根因尚未定位。

**计费**：排障期间用 `model_call_budget` 限制了请求次数，但超时请求是否计费取决于服务商，需由团队查看服务商 usage/billing。修复后的 6 次请求都有本地 token usage 可核验（见上表）。
