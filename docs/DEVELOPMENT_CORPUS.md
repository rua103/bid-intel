# 开发集与实验记录

`backend/app/corpus.py` 是受限速率的公开开发集采集器。它只允许 `ccgp.gov.cn`，默认每次请求至少间隔 1 秒，记录来源 URL、响应状态、下载时间、文件大小和 SHA-256；第三方附件域名会被明确记录为跳过。采集器不访问官方隐藏评测集，也不把公开开发集当作官方成绩。

2026-09-24 已按中标/成交公告路径重新采集一份开发集：站点当前列表提供 20 条公告，清单位于本机 `backend/.data/development-clean/`，原始文件不纳入 Git。旧目录保留作为审计记录，但包含误发现的站内资讯，不用于实验。

`docs/benchmarks/clean-compare-3.json` 是其中 3 条公告的规则、纯模型和混合方案对比。规则抽取正常完成；当时 DeepSeek 的 6 次请求全部 `ReadTimeout`，成功响应数为 0，所以这份文件不能被解释为模型准确率。

`docs/benchmarks/synthetic-1000.md` 是离线合成压测：1000 条公告、2000 条标的、3000 条显式注入投标记录。它用于建立 SQLite 查询基线，不用于证明抽取准确率。五个场景的 warm p95 都低于 1 秒，最慢的共同投标项目查询约 325 ms。

## DeepSeek 抽取超时跟进（2026-09-24）

截至本次记录，当前本机保存的模型配置名为 `deepseek-v4-flash`（旧实验记录用的是 `deepseek-v4-pro`）。API 地址和 Key 的连通性测试返回成功；一次简短 JSON ping 返回 HTTP 200，耗时约 3.4 秒。因此目前没有证据表明是 API 地址或 Key 错误。

真实公告抽取仍无法稳定完成。把超时从 45 秒提高到 120 秒后，两条测试公告仍各自触发 `ReadTimeout`：一条有 30 条规则表格候选，另一条有 3 条规则表格候选。失败时服务没有返回 usage，故拿不到 token 统计；超时不是零条抽取结果，不能计作模型准确率为零。一条约 700 字符的真实公告片段诊断曾收到 HTTP 200 和约 5.5 KB 响应，但本地诊断代码处理响应时抛出 `TypeError`，没有通过抽取 schema 校验，因此也不能算一次成功抽取。

源码当前默认 `MODEL_TIMEOUT_SECONDS=120`，抽取请求另加了 `thinking.type=disabled` 和 `max_tokens=4096`。同一条三候选公告在这项改动后仍超时，所以“关闭思考模式”尚未解决问题。之后启动的流式接口诊断在本次交接前被中止，没有可报告结果。建议下一位接手者先确认该模型/服务商对 `thinking`、JSON 输出和流式响应的支持方式，再用一个极短的结构化抽取请求检查完整响应是否符合 `ModelExtractionPayload`；成功前不要批量调用 20 条。

测试期间使用 `model_call_budget` 限制了模型请求次数，但超时请求是否计费取决于服务商，需由团队查看服务商 usage/billing。除简短 ping 的返回 usage 外，其余失败请求没有本地 token usage 可核验。

当前仍有可复用的真实开发集、标注工作台、抽取/评测管线和 1000 条合成压测报告；尚未完成 20 条人工 gold，也没有可宣称的真实模型准确率。真实公告只能先作为开发/标注材料，不等于官方基准或官方成绩。
