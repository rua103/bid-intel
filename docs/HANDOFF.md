## 一、这个项目在做什么

赛题五：**面向行业数据的智能实体挖掘与关系建模**。从政府采购公告（正文 + 附件）里：

1. **任务一（40 分）** 抽取标的物七字段：产品/服务名称、品目、品牌、规格型号、数量、单价、总价；以及投标主体和中标结果。
2. **任务二（25 分）** 构建并查询五类关系：采购单位合作供应商、高频投标主体、中标供应商的共同竞标者、多家供应商的共同采购单位、多家供应商的共同投标项目。
3. **任务三（25 分）** 可视化平台，把上面的结果查出来、看得见。
4. 综合印象 10 分。

计分口径（来自赛题原文）：**准确性 = 准确率 × 0.4 + 精确率 × 0.3 + 召回率 × 0.3**；任务一另有**处理速率 5 分**。
技术栈：Python/FastAPI + SQLite（Neo4j 可选）+ Vue3。模型必须是赛题允许的 **Qwen/DeepSeek 系列**（代码里有校验，模型名不以 qwen/deepseek 开头会直接跳过）。

## 四、当前最该盯的问题（按优先级）

### P0-1 · 实体名称归一化 / 别名 —— 任务一 + 任务二 的共同命门

`storage.py` 的 `_normalized_entity_name()` 目前只做「去空白 + 转小写」，**没有任何模糊合并**；`organization_aliases` 表虽然建了，但 `_upsert_organization()` 写进去的别名永远等于规范名，等于空转。

真实公告里同一主体会出现「北京XX科技有限公司」/「XX科技」/带括号后缀等变体。一旦不合并：

- 五类查询会**系统性欠计**——共同投标（co-bidder）、共同采购单位（common-buyer）场景直接漏配；
- 任务二的 25 分大面积丢分。

**注意**：代码注释里"等官方参考数据再合并"的保守判断是对的，别一上来就上模糊匹配。正确做法是**规则归一（统一"有限公司/有限责任公司"后缀、去括号、全半角）+ 别名人工确认入口**，让金标里明确同一主体。

### P0-2 · 一条金标都还没有

`backend/.data/development-clean/` 里有 **20 条真实公开公告**（来自 ccgp.gov.cn，含原文 + SHA-256 溯源，**不进 Git**）。这是官方数据的替身：同领域、同格式。

用标注工作台逐条核验，产出 20～50 条 gold，就能算出**第一份有意义的准确率/精确率/召回率**。官方数据到了只是换语料，管线一行不用改。

> ⚠️ 标注集要分两份：**调优/提示集** 与 **留出验证集**。混在一起自欺欺人。

### P0-3 · 五类查询口径待官方确认

`QUERY_SEMANTICS.md` 末尾列了 6 条必须用官方样例/基准确认的歧义，最关键的两条：

- 频次按**公告、项目还是采购包**算？
- 场景二/三的"参与投标主体"**是否包含中标方**？（赛题术语表把"投标参与方"专指未中标方，这里极易理解错）

**不要把推测值写进正式基准结果。**

### P1 · 模型抽取太慢（处理速率 5 分）

`ingestion.py` 的 `_ingest_expanded()` 是「**每个 document 一次模型调用，且完全串行**」：

- 一条公告带 3 个附件 = 4 次**串行**调用；
- 每次把**规则解析已经完美处理的表格文本**也一起塞进模型（`MODEL_MAX_CHARS` 默认 12000）；
- 20 条公告 ≈ 60+ 次串行调用。

优化方向（按预期收益排序）：**只送规则未覆盖的残差文本** → **并发调用** → **按内容哈希缓存** → 按需跳过模型。

### P2 · 其它已知欠账

- **OCR 依赖 Tesseract 系统程序**（`parsers.py` 用 `shutil.which("tesseract")`），pip 装不了，还要装 `chi_sim` 语言包，**README 里没写**。队友开了 `ocr_enabled=True` 只会看到一串"未找到 Tesseract"。若官方数据确有扫描件，建议换 `rapidocr-onnxruntime`（与 PaddleOCR 同款 PP-OCR 模型、pip 可装）。
- **Neo4j 只到 CLI**：`graph.py` 有完整的 `sync_to_neo4j`/`query_neo4j`，但没暴露成 API，前端展示走的是 SQLite 投影。想现场演示 Neo4j 需要补一个可选开关。
- **前端 echarts 全量打包**（单 JS 1.14 MB / gzip 383 KB）。演示用 `npm run dev` 不受影响，属"有余力再优化"。

## 五、今天修了什么（重要，别改回去）

模型抽取此前**每次请求都失败**。两个独立原因，都已修复：

**① 非流式请求 → 读超时**
`httpx` 的 `timeout` 是**读超时**（等下一块字节），非流式下服务端生成完成前不发任何字节，于是读超时退化成"整段生成总时长上限"。证据：6 次请求全部 `ReadTimeout`，耗时齐刷刷停在 **45.7~45.9 秒**。
→ 改为 `httpx.stream` + SSE 累积。超时语义随之变为**块间隔**（`MODEL_TIMEOUT_SECONDS=120`），另加 `MODEL_STREAM_TOTAL_SECONDS=600` 作兜底。流式响应里的 `reasoning_content` **必须丢弃**，否则推理文本会污染 JSON。

**② `thinking: {"type": "disabled"}` → 空输出 + 3 倍延迟**
有人为了"关掉思考模式提速"加了这个参数，实测**适得其反**（同一网关、同一句话）：

| 变体 | 总耗时 | 推理 token | 输出内容 |
|---|---|---|---|
| 带 `thinking:{type:disabled}` | **29.32s** | 548 | **空** ❌ |
| **不带任何 thinking 参数** | **11.02s** | 119 | `{"brand":"品牌A","qty":2}` ✅ |
| 带 `reasoning_effort: none` | 32.48s | 545 | **空** ❌ |

它把整个 `max_tokens` 预算烧在推理上，`content` 返回空串——既会造成"抽不出来"，也会因生成过久而先撞超时。**已删除，并加了回归测试锁死。**

> 🚫 **不要**再往请求里加 `thinking` 或 `reasoning_effort`。要加必须先重新实测这三个数字。

## 六、队友不写代码也能做的事

**去标数据。** 前端「05 人工标注与质量评测」面板就是干这个的：

1. 选材料 → 生成候选草稿（可选 rules / model / hybrid 三种方案）；
2. **对照左侧原文逐条修正**右侧七字段、中标方、投标主体；
3. 勾选"我已对照原文核验"，导出 `gold.reviewed.json`。

也可以直接导入已有的 gold / predictions JSON 跑指标。

**规矩**：自动抽取结果**永远不能**直接当人工标准答案；空白表示原文未披露，不是"没有"；金额统一为元；中标方要**同时**列入投标主体。

## 七、本地跑起来

```powershell
cd backend
py -3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
uvicorn app.main:app --reload
```

```powershell
cd frontend
npm ci
npm run dev
```

打开 `http://localhost:5173`；API 文档在 `http://127.0.0.1:8000/docs`。

模型配置**可以直接在网页「模型配置」面板填**（写入 `backend/.data/model_config.json`，重启不丢；`backend/.env` 作兜底）。页面只显示打码尾号。
