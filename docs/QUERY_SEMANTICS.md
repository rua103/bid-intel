# 数据模型与查询口径

> **依据为赛题原文与赛题答疑表。** 原文确定任务范围，答疑补充品牌/产品供应商和投标参与方等口径；未明确的边界保留为团队选择与残余风险，不当作官方结论。
>
> 命题方已提供任务基准原始 HTML 与附件，**不提供逐条 Gold / ground-truth**；评分基准约 100 条，题目说明“不对外发放，仅用于评分”。本文引用的 Gold 均由团队自行核验，只能支持本地实现验证。
>
> 当前口径更新于 **2026-10-08**。历史验证不能自动证明答疑迁移后的实现，具体范围见第五节。

## 一、赛题原文与答疑确定的口径

### 1.1 投标参与方 = 所有已记录参与主体

> 术语表：「**投标参与方**：响应招标公告、提交投标文件并参与竞争的法人或其他组织，
> **本题目中特指参与投标但未中标的主体**。」

**答疑口径**：参与投标“中与不中都算”。场景二、场景三及关系线索默认保留
`winner`、`nonwinner`、`unknown` 三类已记录主体；`unknown` 表示参加但结果未披露，
不能显示为未中标。

实现已按答疑口径收敛：[`main.py`](../backend/app/main.py) 与
[`analytics.py`](../backend/app/analytics.py) 的 `include_winners` **默认为 `True`**，
即默认保留 winner、nonwinner、unknown；API 仍保留 `include_winners=false`
作为显式的“仅明确未中标（`nonwinner`）”筛选选项，此时不包含 `unknown`。
场景三的包明细仍保留所有已记录的主体和结果，便于核验联合中标等情况。

数据层不受影响：gold 的 `bidders` 记录全部投标主体并带 `outcome` 标签，是超集；过滤发生在查询侧。

### 1.2 场景 2 / 3 / 5 的频次单位是「项目」

> 场景（2）：「指定任意采购单位，查询并输出其**历史招标项目中**高频（TOP5）参与投标的主体…」
> 场景（3）：「指定任意中标供应商…其**历史项目中**高频（TOP5）共同竞标的主体…」
> 场景（5）：「…其历史共同参与竞标的**项目**信息与竞标结果，包含**项目数量、项目总金额**…」

**后果**：这三场景按**项目**计频次，不是按采购包。

SQLite 场景二/三现按 `COUNT(DISTINCT project.id)` 计频；场景五仍按共同投标包返回明细，
同时用去重后的项目数汇总。多包项目里的同一主体或主体组合只计一个项目。
查询侧的 Neo4j Cypher 模板也已改为项目粒度；Neo4j 在线 API 通过 `ANALYTICS_BACKEND=neo4j` 选择，连接或同步失败时按请求回退 SQLite。

当前答疑口径的 SQLite 独立 oracle 校验见 `backend/.data/query-validation/qa-semantics-20261007-v2.json`：24 条 reviewed Gold、五场景 **6471/6471** 项通过。该报告没有运行 Neo4j。历史上项目粒度修复前场景二 9/48、场景三 6/74 个查询不符；旧口径的双后端对照是另一份证据，详见第五节。

### 1.3 中标供应商不唯一

> 术语表：「中标供应商…**若项目涉及联合体投标、分标段招标等，则中标供应商可能有多个**。」

**后果**：一个包可以有多个中标方，`awards` 按 (包, 供应商) 记录，不假设唯一。

### 1.4 场景一的产品供应商采用任务一品牌字段

答疑第 3 条明确“产品供应商就是任务一的品牌字段”，第 9 条要求场景一同时展示中标供应商和产品供应商。因此 `product_suppliers` 按 `procurement_items.brand` 原值聚合，分别返回项目数、采购包数、明确标的总价和来源证据。这里的产品供应商是题目规定的品牌口径，**不是自动识别出的生产商、经销商或其他法律实体**。

产品供应商金额仅累计该品牌标的行中明确披露的 `total_price`；不分摊或复制 `awards` 的中标交易额，不用数量、单价反推缺失总价。品牌或金额未披露时保留缺失边界，不能将未知金额解释为真实的零元交易。中标供应商仍独立使用组织及中标记录统计。

## 二、团队选择与未明确边界

以下未被原文和答疑完整形式化，技术路线报告应写明当前选择、证据和风险。

| 项 | 我们的口径 | 理由 | 残余风险 |
|---|---|---|---|
| **场景 1 / 4 的频次单位** | 当前合作频次按采购包，另保留项目数 | 场景文字未逐项形式化计数方式，但术语表把合作频次描述为“历史项目中发生合作或共同参与竞标的次数”；当前保留较细包级证据 | 同一项目多包时包级频次更大，不能称已与官方项目口径对齐 |
| **"项目金额"取哪个** | 场景内分别列出，不做单一替换 | 原文在场景 1/4 说"交易总金额"、场景 5 说"项目总金额"，未指明对应预算还是成交额 | 口径可能与官方不一致 |
| **多包 / 多中标人** | 保留包结构，不合并；金额按唯一中标记录汇总，不重复分配 | 联合体成员不拆分，避免同一笔中标额重复计入 | — |
| **废标 / 撤回 / 重复与更正公告** | 只取明确记载实际成交结果的材料；更正公告优先 | 招标文件、需求表、空白模板不算成交事实 | 更正关系若原文未标"更正"，无法自动识别 |
| **资格性/符合性审查失败** | 只有明确主体和评审结果证据时保留其状态；模糊参与结果使用 `unknown` 并保留来源 | 答疑没有正式裁决失败主体是否计入参与统计；默认统计已记录参与主体 | 不能仅凭审查表标题判定参加或落标，现场口径可能要求另行过滤 |
| **跨包协同** | 同一包形成共同参与组合，再按项目去重计频；保留包明细 | 项目粒度与包内实际共同参与的证据分开 | 同一项目不同包的两个主体不会仅因同属项目自动组成共同投标；是否应计入仍未获官方裁决 |
| **租赁分类** | 仅按原文明示的品目或服务属性填写 | 答疑没有给出统一租赁分类规则 | 不凭“租赁”一词推定货物/服务分类 |

## 三、数据模型

- `organizations` 保存规范显示名；采购单位、中标方、投标方是**关系角色**，不是互斥的组织类型。场景一产品供应商来自标的 `brand` 聚合，不因此创建或合并法律实体组织。
- `organization_aliases` 保存公告原名与来源。**当前仅去空白、大小写归一**；没有可靠证据时不合并分公司、简称或相似名称。
- `projects` 保存公告/项目、采购单位、预算和公告成交总额；两种金额分列。
- `packages` 保存采购包；没有包信息时创建一个 `default` 包。
- `bid_participations` 保存主体的投标结果状态：`winner` / `nonwinner` / `unknown`。**`unknown` 不等于未中标**（原文没说结果的，不能推定落标）。
- `awards` 按 (包, 供应商) 保存中标供应商和可确认的供应商级中标金额。
- `procurement_items` 保存七项标的字段和来源文件、行号、原文证据。

## 四、包号口径

**包号 = 原文明确标签归一后的稳定值**（数字或字母），不带「包」字：

```
原文「合同包1」  →  1
原文「包B」      →  B
原文「A包」      →  A
原文明确给出名称标签（「分包名称： 教学仪器」）→ 只有在连续原文证据保留且通过校验时才用名称本身
原文只有项目标题、品目名、邻近文字或「见附件」→ `default`
```

**理由**：评测在 `notice_id + package_id` 内精确匹配。标注侧与解析侧产出不同的字符串时，一条都对不上，
整个公告会被同时记成"全部漏报 + 全部多报"——实测这种状态下加权分只有 1.7%，**那是假数字，不是准确率**。

名称型包号必须同时有明确的「分包名称/标段名称/采购包名称/包名称/包名」标签和值的连续证据；模型输出的 `package_source_evidence` 会被再次校验。当前不使用“包名等于品目名”的推断，也不恢复宽松邻近文本正则。详见 [GAP_ANALYSIS.md](GAP_ANALYSIS.md) 1.18、1.19。

## 五、在线分析后端边界

SQLite 是写入源和默认分析后端。设置 `ANALYTICS_BACKEND=neo4j` 后，五类分析 API 使用按 `X-Dataset-ID` 隔离的 Neo4j 镜像；同步、连接或查询失败时按请求回退 SQLite，并用响应头 `X-Analytics-Backend` 标记实际后端。场景二/三及关系线索默认统计 `winner`、`nonwinner`、`unknown`，场景二/三/五按项目去重，场景三/五金额按唯一 award 记录汇总。

`/api/v1/graph` 的关系图投影及关系线索接口继续读取 SQLite，不随分析后端配置切换。

验证证据分为两份，不能因检查数量相同而混用：

- **历史双后端一致性**：`neo4j-release-db05fe5aca8b4215a0b5fb6a94a1d774.json` 在当时默认仅 `nonwinner` 的口径下验证 SQLite/Neo4j 各 `6471/6471`，响应无差异；导入 442 节点、464 关系。它不证明本轮答疑迁移后的 Neo4j 全量 Gold 结果。
- **当前 SQLite oracle**：`qa-semantics-20261007-v2.json` 从 24 条 reviewed Gold 独立计算期望结果，并对 `SQLite app.analytics` 做 `6471/6471` 比较，导入 24 项目、39 包、251 标的、111 参与记录及 39 中标记录。报告明确 `Neo4j was not exercised`；其中关于生产查询只走 SQLite 的旧注释不能覆盖现有可选 Neo4j 架构。

这两份报告都是团队本地验证证据，不证明官方隐藏答案或 1038 条字段抽取正确。2026-10-08 统一验收在 Docker Neo4j 5.26.14 下通过后端全量 `361 passed、0 skipped`，图模块定向 `9 passed`，覆盖五类 API、无中标记录的品牌标的、精确金额、空值和数据集隔离；没有把该合成集成结果计为重跑了 Gold 全量对照。
