# GAP 6a：五类关系查询 Gold 校验

**日期：** 2026-09-27
**范围：** SQLite `app.analytics` 五类查询；24 条 `reviewed` gold；未调用抽取模型。

## 方法

验证脚本把 Gold 转成 24 个项目、39 个包、251 条标的、111 条投标参与关系和 39 条中标关系，写入新建的本地 SQLite 文件。数据库位于忽略目录 `backend/.data/query-validation/`，不读取或改写默认业务库。

期望值由 `gold.merged.json` 直接计算，没调用 `analytics.py` 的查询或评测函数。组织对齐沿用存储层的保守规则：去空白并忽略大小写，不做模糊别名合并。Gold 的 `entity_id` 是标注提及 ID，同一名称可能对应多个 ID，因此不能将其误作跨公告的规范组织 ID。

覆盖范围：

| 场景 | 比较项 | 查询次数 |
|---|---|---:|
| 1. 采购单位—中标供应商 | 24 个采购单位下的中标主体、包数、金额、品牌 | 24 |
| 2. 高频投标主体及组合 | 24 个采购单位，分别验证默认过滤和完整参与者模式 | 48 |
| 3. 中标供应商共同竞标方 | 37 家中标供应商，分别验证默认过滤和完整参与者模式 | 74 |
| 4. 多家中标供应商共同服务的采购单位 | 全部 666 个供应商对，另测 7 个三家组合 | 673 |
| 5. 多主体共同投标项目 | 全部 5356 个参与方对，另测 296 个三方组合 | 5652 |
| **合计** |  | **6471** |

## 发现与修复

修复前，场景 1、4、5 在本次 gold 上的关系和金额检查通过；场景 2 有 **9/48** 次不匹配，场景 3 有 **6/74** 次不匹配。根因有两项：

- 场景 2/3 按包计频，多包项目会重复计数；赛题要求按项目统计。
- 默认条件 `outcome != 'winner'` 把 Gold 中 19 条 `unknown` 结果也算成未中标主体。默认查询现在只纳入明确标成 `nonwinner` 的主体；显式 `include_winners=true` 仍返回所有状态。

SQLite 查询、Neo4j Cypher 模板和前端计数标签已同步改为项目粒度。场景 5 继续返回共同参与的包明细，并按不同项目去重汇总 `project_count`。

## 结果

修复后 **6471/6471 项通过**：场景 1 为 24/24，场景 2 为 48/48，场景 3 为 74/74，场景 4 为 673/673，场景 5 为 5652/5652。Gold 文件 SHA-256：

## 可复跑与边界

在 `backend/` 下执行：

```powershell
.venv/Scripts/python.exe -m scripts.validate_gold_queries
```

脚本会拒绝覆盖已有数据库或报告，创建新的隔离 SQLite 文件；JSON 结果会打印到终端，并默认保存到同一忽略目录，也可用 `--report <新文件路径>` 改写输出位置。此次生成的逐项 JSON 和 SQLite 文件保存在本机忽略目录，不含在 Git 中。

这项结果验证的是 SQLite 当前返回的关系、频次、包明细及金额字段在 24 条人工 gold 上与声明口径的一致性；它不证明 gold 之外的公告分布表现，也没有验证 Neo4j 的实际运行、模糊实体归一化或界面端到端 API 响应。该比较不把尚未实现的汇总输出算作通过：场景 3 的共同竞标金额展示和场景 5 的项目总金额汇总仍由 GAP 2.5/2.6 跟踪。Neo4j 运行验证仍由 GAP 2.3 跟踪。
